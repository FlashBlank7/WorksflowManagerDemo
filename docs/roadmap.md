# 路线图

最后更新 2026-08-28。做过什么在下面按版本列；接下来打算做什么在最后一节。

## 不变的锚

薄客户端 + 自托管后端。三件事：

1. **工作流生成** —— 说人话，得到一个活的工作流
2. **统筹管理** —— 今日运行、定时任务、失败与趋势一眼清
3. **对话式使用** —— CLI 是招牌，网页是同一能力的另一张脸

能力一律在服务端执行并入审计台账，客户端无法伪造结果。
界面与语气的取舍另见 [design.md](design.md)。

## v0.8 —— 候选池

清单来自**真实使用中撞到的**，不是想象出来的功能表。
做掉一条就移出去一条——候选池不跟上就会变成许愿墙。

**用起来会绊一下的**

- 归档列表只能按名字过滤，找不到「上周收的那些」这类时间维度的说法
- 多档案汇总：有两个环境的人得切来切去（现在只有一个后端，先不做）

**还没验证过的**

- 真实多用户：所有测试都是单人跑的，权限边界没被真正压过
- 别人的后端：接口清单写了，`guanjia doctor --contract` 也能自查了，
  但还没有第二个实现真正验证过它够不够用
- 长期运行：**今天部分验过了，结论不好看**。事件表涨到 1 GB
  （用量事件把整条任务的用量历史抄了一份，平方级增长），
  启动时的归档要全表扫，一次 90 分钟。三处都修了
  （维护挪到后台、加索引、事件瘦身），但仍没见过「连跑一个月」的样子——
  磁盘慢的机器上尤其要盯着

## 原则

每个 5 分钟循环 tick 交付一个完整小切片（能跑、能验、有提交）；
不为动而动；界面改动保持零依赖纯标准库底线。
