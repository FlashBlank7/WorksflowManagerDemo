# 必填输入在客户端拦，不在平台核心拦

**结论**：三条用户出口（对话管家 / `guanjia run` / 网页壳）各自在发请求前
检查必填输入；平台的 `create_run` 不加校验。

## 为什么要拦

少给一个必填参数，远端会照建一条运行记录，然后在 start 节点失败。
那条失败**永久留在业主的运行历史里**，还会喂给体检和「近期失败」面板——
看起来像是工作流坏了，其实只是调用时少给了一个字段。

真机上这是排第一的失败原因（`缺少必填输入 text` ×5、`sales` ×4）。
报错还指向下游节点：`node start failed: missing required input: text`，
业主看到的是节点名，不是「你少给了 text」。

## 为什么不在平台核心拦

在 `create_run` 上加校验最"干净"，但被否决了：

- **验收有意跑注定失败的用例**。验收规格支持 `expect_run: "failed"`
  （"业主明确说这种输入就该报错"）。在所有运行都要经过的那条路上加拦截，
  就得给验收开一个 opt-out 参数，把两个模块耦起来。
- **爆炸半径不成比例**。`create_run` 是调度、嵌套工作流、API、验收、
  测试全都要走的核心路径。为了挡住一类调用方失误，去动它不划算。
- **收益已经拿到了**。三条出口都是人在用的入口，堵住就没有误建的运行了。
  直接调 API 的程序化调用方知道自己在干什么，失败记录对它们是有意义的信号。

## 代价（明写出来）

- 逻辑有三份（Python 两处 + `app.js` 一处），改一处要记得改另两处。
- 第三方客户端不会自动获得这层保护——它们仍然可能造出注定失败的运行。

如果将来出口多到管不过来，再回头做「核心校验 + 显式 opt-out」；
那时的触发条件应该是"又多了两三个出口"，而不是"看起来更整洁"。
