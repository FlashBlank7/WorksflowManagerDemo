# guanjia 和它的近邻们

> 范本致敬 gptme 的 alternatives 页：替你回答"这和 X 有什么区别"，省掉重复 issue。
> 对齐版本：0.6.1（2026-08-28）。

## 一句话定位

**guanjia：终端里说人话，远端工厂替你造出能跑、有定时、可监控的工作流。**
交付物是持续运行的工作流，不是一段代码、不是一次执行。

## 对话式终端智能体

| 工具 | 它的取向 | 和 guanjia 的分野 |
| --- | --- | --- |
| aichat | 全能终端 LLM 工作站（Shell 助手/RAG/Agents） | 它执行完就结束；guanjia 的产出**持续存在**——有版本、有定时、有审计 |
| gptme | 模型无关的终端助手，持久自治智能体 | 同上；且 guanjia 的智能体循环在**服务端**，客户端薄到可审计 |
| open-interpreter | 给 LLM 一个 exec()，操作整台电脑 | guanjia 恰恰**不让**模型直接碰你的电脑——本地零执行，能力全在远端受控运行时 |
| aider / claude-code 类 | 编码智能体，产出代码 | guanjia 面向**业务交付物**（报表/对账/监控），用户可以完全不懂代码 |

## 工作流引擎的 CLI

| 工具 | 它的取向 | 和 guanjia 的分野 |
| --- | --- | --- |
| n8n CLI | import/export/execute 运维面 | n8n 的 AI 建流程在网页编辑器；guanjia 的**生成与管理都在对话里** |
| windmill (wmill) | 脚本/flow 当代码同步部署 | wmill 面向工程师的 CI；guanjia 面向"说需求的人" |
| temporal CLI | 工作流开发者的运维终端 | temporal 编排你写的代码；guanjia **替你把工作流造出来** |

## 造出来之后呢——这块才是真正的分野

大多数"AI 生成工作流"的工具在**交付那一刻就结束了**。而工作流的麻烦事几乎都在之后：
它某天开始失败、定时悄悄不再触发、上游改了字段。guanjia 把这段做成了闭环：

| 环节 | guanjia 怎么做 | 通常的做法 |
| --- | --- | --- |
| **发现** | 体检判 broken（窗口内全败/最近连败）与 stale（有定时却没按时开火），带最近一次失败原因 | 看运行列表，自己数 |
| **说清** | 四个入口同一份视图：`doctor`、`today`、网页统筹页、对话里问"有什么坏了吗" | 翻日志 |
| **修好** | 对话里说"X 坏了帮我修"，构建智能体读**现有草稿**改（不推倒重来），补上覆盖该故障的验收用例后重新发布 | 人工重做 |
| **根因** | 定时不开火时自动查调度器死活，按结果分流建议——是配置没发布，还是调度器挂了 | 猜 |
| **告知** | 离场有 webhook、在场有浏览器通知、还能让它自己搭一个每日失败摘要工作流 | 自己接监控 |

真实案例（仓库里有完整记录）：一个已发布工作流连续 6 次运行全败，
体检点名并给出原因「公式包含不支持的字符 `.`」；在对话里说一句"帮我修"，
构建智能体不但改掉了那个字符，还找出了报错没提到的真正病根
（终端节点的输出填的是类型名而不是数据引用），修完发布 v3，两次真跑成功。

## 凭什么可信（不是又一个套壳）

- **生成不是文本生成**：远端的构建智能体在受控 harness 里增量搭建——每个节点过 schema 校验、
  每次验收测试锚定真实数字、失败诚实报告（"空结果诚实"是家法）；
- **智能体不自证**：工具全在服务端执行并入审计台账，答案里的数字都能溯源到账本；
- **本地零信任负担**：客户端纯标准库零依赖、不跑模型、不存业务数据——`uvx guanjia` 免装可验；
- **缺陷公开**：[已知边界](known-limits.md) 列着现在确实做不到的事（必须自托管、
  Windows/移动端未验证、依赖平台版本的功能会降级），不藏。

## 一个可能对同类项目有用的发现

搭建质量的瓶颈常常不在模型，而在**积木库的能力缺口**。

实测：公式引擎原本没有任何字符串函数，于是"数一段文本有几行"在积木层没有确定性解法。
构建智能体依次探索了公式、正则抽取、Bash 沙箱三条路，全部走死后被迫改用 LLM 数数
——既不确定、又按次收费。给引擎补上 `trim/split/count` 之后，**同一句需求的搭建时间从
24.4 分钟降到 40 秒（36×），运行期模型开销归零，同输入两次结果完全一致**。

结论：对智能体搭建的系统，先补原语的能力缺口，比换更强的模型划算得多。

（这条来自一次对照实验：同一句需求、同一个模型，只改积木库。
修复前构建智能体依次尝试公式、正则、沙箱三条路全部走死，
最后用 LLM 数行数——不确定且按次计费；补上三个字符串函数后，
同一需求 40 秒完成、运行期零模型调用、同输入两次结果完全一致。）
